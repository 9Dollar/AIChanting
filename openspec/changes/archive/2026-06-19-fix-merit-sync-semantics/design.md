## Context

当前系统存在功德同步语义不一致的 bug：

- **后端** `server/db.js` 的 `upsertUser` 和 `upsertModel` 都采用**累加语义**：`newMerit = existing.total_merit + merit`。
- **前端** `src/app.js` 的 `syncToServer` 传的是**当前总功德**：`merit: userMerit.toString()`。

两者语义错配导致：用户每次点击"同步服务器"，功德被重复累加。实测中一个 model 只 POST 一次 `merit:1500`，服务器返回 `1760`（1500 + 历史 260）。

此外，当前前端只在用户手动点击"同步服务器"时一次性上传用户功德 + 最近一条记录的模型功德，模型功德上传粒度粗、易丢失，且与"每次诵经完成"的自然时机脱节。

后端写操作目前无并发保护：`better-sqlite3` 虽是同步 API（单线程内天然串行），但若未来引入多实例或异步路径，存在丢失更新风险。本次变更显式引入操作队列，把并发安全从"靠巧合"提升为"靠设计"。

## Goals / Non-Goals

**Goals:**
- 修正功德同步语义错配 bug，使模型功德（增量）与用户功德（全量）各自走正确路径。
- 模型功德在每次诵经完成时自动增量上传，后端累加。
- 用户功德由用户主动点击"上传用户数据"按钮全量上传，后端覆盖。
- 后端模型功德与用户功德解耦：用户上传时只更新 users 表，不动 models 表。
- 后端引入显式并发保护（全局操作队列），串行化对同一记录的写操作。
- 前端 localStorage 保存用户完整数据（用户功德 + 各模型功德明细）。

**Non-Goals:**
- 不引入用户认证/鉴权（项目明确"不防作弊，心诚则灵"）。
- 不修复历史 `db.sqlite` 中已被错误累加的数据（提供清理方式，但不自动回溯）。
- 不改变功德计算公式、虔诚系数、经文基础功德等业务规则。
- 不引入分布式锁或 Redis（单实例 SQLite 场景，进程内队列足够）。
- 不改变 API 端点路径，只改变请求体语义。

## Decisions

### 决策 1：模型功德 = 增量 + 自动；用户功德 = 全量 + 手动

**选择**：两条功德走不同路径。
- 模型功德：诵经循环内，每次完成后立即 POST 增量（本次新增功德），后端累加。
- 用户功德：用户点击"上传用户数据"按钮时 POST 全量（当前总功德），后端覆盖。

**理由**：
- 模型功德是"公共账本"，多个用户贡献同一模型，增量累加是唯一正确语义。
- 用户功德是"个人账本"，前端 localStorage 是 source of truth，上传是同步个人全量状态，覆盖语义最自然，且天然幂等（重复上传不会膨胀）。
- 手动上传用户数据符合"用户自行决定是否上传"的隐私诉求。

**备选方案**：
- A. 全部改增量：用户功德也传增量。但前端 localStorage 已存全量，算增量需额外记录"上次上传了多少"，复杂且易错。
- B. 全部改全量：模型功德也传全量。但模型功德是多用户共享的，单个用户无法知道"模型总功德"，无法传全量。

### 决策 2：后端 `upsertUser` 改覆盖式，`upsertModel` 保持累加式

**选择**：
- `upsertUser(userId, userName, merit, chantCount)`：存在则用传入值直接覆盖 `total_merit` / `chant_count` / `user_name`；不存在则插入。
- `upsertModel(name, provider, merit, chantCount)`：保持现有累加逻辑。

**理由**：与决策 1 的语义对齐。用户功德全量上传 → 覆盖；模型功德增量上传 → 累加。

### 决策 3：并发保护用进程内全局操作队列（Promise 链）

**选择**：在后端 db 层之上引入一个全局操作队列，所有写操作（upsertUser / upsertModel）入队串行执行。实现为单条 Promise 链：每个操作 `queue = queue.then(() => doWrite())`。

**理由**：
- `better-sqlite3` 是同步 API，单线程内本就串行，但显式队列把"并发安全"从隐式变为显式，防御未来重构（如改异步驱动、加多 worker）。
- 单实例 SQLite 不需要分布式锁，进程内队列零依赖、零成本。
- 队列粒度：全局单队列（非 per-key）。SQLite 单文件写入本就是全局串行，per-key 队列增加复杂度无收益。

**备选方案**：
- A. per-key 锁（按 userId / modelKey 分队列）：理论并发更高，但 SQLite 单写者锁使收益归零，徒增复杂度。
- B. 事务包裹：`better-sqlite3` 已用 prepared statement，事务粒度太细，无法覆盖"读-改-写"的跨语句竞态。
- C. 乐观锁（version 字段）：需改表结构，过度设计。

### 决策 4：前端 localStorage 数据结构扩展

**选择**：用户数据结构在现有基础上明确包含 `byModel` 明细：

```javascript
{
  id, name, createdAt,
  totalMerit,          // 用户总功德（BigInt 字符串）
  chantCount,          // 总诵经次数
  byScripture: {},     // 各经文功德
  byModel: {           // 各模型功德明细（用户视角）
    [modelKey]: { provider, model, merit, chantCount }
  },
  records: []
}
```

**理由**：用户上传数据时，`byModel` 可作为"用户贡献明细"附加上传（虽然后端 models 表不在此路径更新，但保留明细供未来扩展和用户自查看）。本次后端用户上传接口只消费 `totalMerit` / `chantCount`，`byModel` 暂存不消费。

### 决策 5：API 契约文档化区分全量/增量

**选择**：在 `server/routes/merit.js` 顶部注释和 proposal/spec 中明确标注：
- `POST /api/user/merit`：请求体 `merit` = 用户当前总功德（全量），后端覆盖。
- `POST /api/model/merit`：请求体 `merit` = 本次新增功德（增量），后端累加。

**理由**：两个端点路径几乎一样，语义却相反，必须显式文档化防止再次错配。

## Risks / Trade-offs

- **[历史脏数据]** 现有 `db.sqlite` 中因 bug 累加错误的数据无法自动修正。
  → 缓解：tasks 中提供清理脚本（删除 db.sqlite 重新建表，或提供 reset API），由用户决定是否重置。

- **[模型功德增量请求失败丢失]** 每次诵经完成发请求，若网络失败，该次增量永久丢失（后端没收到）。
  → 缓解：前端记录"未同步的模型功德增量"，失败时保留在 localStorage 队列，下次诵经完成时合并重试。本次实现该重试队列（轻量）。

- **[用户功德覆盖可能回退]** 若用户在设备 A 上传 1000，换设备 B（本地 500）后上传，会把服务器从 1000 覆盖为 500。
  → 缓解：这是"用户自决上传"的固有代价，spec 中明确说明。前端可在上传前对比服务器值给出提示（本次实现可选，非必须）。

- **[全局队列成为瓶颈]** 所有写操作串行，高并发下排队。
  → 缓解：单实例 SQLite 本就单写者，队列不引入额外瓶颈；若未来需水平扩展，再引入分布式方案。

- **[BREAKING API 语义变更]** `POST /api/user/merit` 从累加变覆盖，旧客户端（若有）行为会变。
  → 缓解：本项目前端后端同仓同步发布，无外部客户端；在 proposal 中标注 BREAKING。

## Migration Plan

1. **部署后端新版本**：`upsertUser` 改覆盖、引入操作队列。部署后旧数据仍在，但语义已变。
2. **清理历史脏数据（可选）**：停止服务 → 删除 `server/db.sqlite` → 重启服务自动建表。或保留脏数据，接受排行榜数值偏大（符合"不防作弊"精神）。
3. **部署前端新版本**：诵经循环接入增量上传 + "上传用户数据"按钮。
4. **回滚策略**：若新版本有问题，回退前后端代码即可；数据库 schema 未变，无需回滚迁移。

## Open Questions

- 用户上传数据时，是否需要在响应中返回"服务器当前值"供前端对比？当前设计不返回（覆盖即生效）。若需"覆盖前提示回退"功能，需后续追加。
- 模型功德增量重试队列的持久化粒度：本次设计存在 localStorage，但页面刷新后是否自动重试未同步增量？默认是（启动时检查并重试）。
