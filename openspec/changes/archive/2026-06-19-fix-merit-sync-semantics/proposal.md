## Why

当前后端 `upsertUser` / `upsertModel` 采用**累加语义**（`existing.total_merit + merit`），而前端 `syncToServer` 传的是**当前总功德**（`userMerit.toString()`）。这导致用户每次点击"同步服务器"按钮，功德都会被重复累加，数值越滚越大。

实测复现：对一个 model 只 POST 一次 `merit:1500`，服务器返回 `total_merit:"1760"`——因为数据库里有历史 `260` 被错误累加。

需要重新定义前后端的功德同步语义，让"模型功德"和"用户功德"走两条不同的、各自语义正确的路径，并引入并发保护避免数据冲突。

## What Changes

- **模型功德：增量同步**。每次诵经完成时，前端立即发一个请求，把**本次新增**的模型功德上传；后端 `upsertModel` 保持累加语义（这才是增量的正确用法）。
- **用户功德：全量上传**。前端 localStorage 保存用户的完整数据（含用户自己的功德，以及用户数据里记录的各模型功德明细）。新增"上传用户数据"按钮，用户主动点击后才上传；后端 `upsertUser` 改为**覆盖式**（用传入值替换，不再累加）。
- **后端模型功德不再在用户上传时更新**。模型功德只通过"每次诵经完成"的增量请求累加，用户数据上传时只更新 users 表，不动 models 表。
- **前端移除旧的"同步服务器"按钮语义**，替换为：诵经循环内自动发增量请求 + 独立的"上传用户数据"按钮。
- **引入并发保护**。后端对 users / models 表的写操作通过全局操作队列（或锁）串行化，避免同一记录并发更新导致丢失更新或脏读。
- **BREAKING**：`POST /api/user/merit` 语义从"累加"变为"覆盖"（请求体含义为用户当前总功德，非增量）。`POST /api/model/merit` 语义保持"累加"（请求体含义为本次新增功德）。

## Capabilities

### New Capabilities
- `merit-sync`: 功德同步能力，定义前端 localStorage 与后端之间模型功德（增量、自动）和用户功德（全量、手动）的同步契约与流程。
- `concurrent-write-protection`: 后端数据库并发写保护，通过全局操作队列串行化对同一记录的更新，避免丢失更新。

## Impact

- **前端 `src/app.js`**：重构 `syncToServer`，拆分为"诵经完成时增量上传模型功德"和"用户主动上传用户数据"两条路径；调整诵经循环在每次完成后触发模型功德增量请求。
- **前端 `src/storage.js`**：确认/调整用户数据结构，确保保存用户功德及各模型功德明细。
- **前端 `src/ui.js`**：将"同步服务器"按钮改为"上传用户数据"按钮，调整事件绑定与文案。
- **后端 `server/db.js`**：`upsertUser` 改为覆盖式；`upsertModel` 保持累加；新增并发保护层（操作队列/锁）。
- **后端 `server/routes/merit.js`**：路由不变，但依赖 db 层的新语义。
- **API 契约**：`POST /api/user/merit` 与 `POST /api/model/merit` 的请求体语义文档化区分（全量 vs 增量）。
- **数据迁移**：现有 `db.sqlite` 中因 bug 累加错误的数据无法自动修正，需手动清理或重置（在 tasks 中说明）。
